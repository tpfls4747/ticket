# 문제 목록 (STEP 3 이후 처리 대상으로 보존)

STEP 2B 에서는 아래 항목을 고치지 않았다. 항목별로 "관찰", "근거", "원인(확인/미확인)"을 구분해 적는다.

## A. 인터랙션 (STEP 3 에서 수정)

### A-1. 화면 간 링크를 누르면 해당 페이지 프레임이 빈 화면이 된다 — 원본에도 있는 문제

> **STEP 3A 에서 해결 (로컬, 미커밋).** 원인 확정: blob 문서에서 상대 경로 href 를 해석할 수 없어 브라우저가 이동을 차단. 같은 자리 화면 전환으로 정상화. `docs/STEP3A_NAV.md` 참고. 아래는 해결 전 기록.

- **관찰:** `<a href="…dc.html">` 링크를 실제 마우스로 누르면 그 페이지의 iframe 이 `about:blank#blocked` 로 이동하고 화면이 비어 버린다. (본문 텍스트 길이 0)
- **근거 (실제 마우스 클릭, 요소 좌표 확인 후 클릭):**

  | 대상 | 원본 | 2A 재번들 | 2B |
  |---|---|---|---|
  | P01 링크 | 이동 (검증 도구 1회) | 이동 (1회) | 이동 (1회) |
  | P07 링크 | 6/6 이동 (프로브, 클릭 시점 2·6·12초 각 2회) | 이동 (1회) | 6/6 이동 (프로브) |
  | P08 링크 | 12/12 이동 (프로브, 클릭 시점 2·6·12초 각 4회) | 이동 (1회) | 12/12 이동 (프로브) |

  "검증 도구 1회"는 `verify/results-2a-reverify/`·`verify/results-2b/` 의 `report.json` `firstLinkClick` 값이다
  (P01·P07·P08 모두 `about:blank#blocked`, 본문 길이 0). P07·P08 의 반복 측정은 `tools/probes/probe_click_target.cjs` 로 했다.
  P01 은 반복 측정을 따로 하지 않았다 (이전에 빗나간 클릭 방식으로 6/6 을 얻었으나 그 값은 신뢰하지 않는다).
- **영향 범위:** 링크는 P01 6개, P07 28개 요소 중 다수, P08 15개 요소 중 다수 (`뒤로`, CTA, 화면 이동). 설계 의도는 "같은 자리에서 다음 화면으로 전환"이지만 번들 안에서는 동작하지 않고 프레임을 지운다.
- **원인:** *미확인.* 추정: 링크가 상대 경로(`Request.dc.html`)라 `blob:` 문서에서 해석되지 못해 브라우저가 이동을 차단하는 것으로 보인다. 런타임(`support.js`)은 `href` 를 정리하는 코드가 있으나 실제로 클릭을 가로채지 못한다. 런타임 코드를 끝까지 추적하지는 않았다.
- **수정 방향 (STEP 3):** 클릭을 가로채 같은 위치에서 화면을 교체하는 처리 추가. 신규 인터랙션이므로 승인 후 진행.

### A-2. 라디오·체크박스는 정상 동작한다 — 문제 아님

- P08 (PairMode 체크박스 2개, 라디오 `mode` 2개, PairSeat 라디오 `dir` 2개)를 실제 마우스로 하나씩 누르면 일반 폼처럼 동작한다. 반복 측정에서 매번 같은 결과(원본 6/6, 재번들 6/6, `tools/probes/probe_controls.cjs`).
- 다만 이 컨트롤들은 다른 화면·상태와 연결되어 있지 않다 (선택해도 CTA 문구·후보 표시가 바뀌지 않음). 연결은 신규 인터랙션이다.

### A-3. 이전 보고의 오류 정정 (측정 도구 문제였음)

STEP 2A 보고서와 `docs/EXTRACTION.md` 초판의 다음 서술은 틀렸고 정정했다.

| 이전 서술 | 실제 | 원인 |
|---|---|---|
| "핸들러가 없어 정적 목업" (STEP 1) | 링크와 네이티브 컨트롤이 구현되어 있다 | `onclick` 만 검색하고 `<a href>` 를 놓침 |
| "P07 링크는 클릭해도 화면 변화 없음" (2A) | 실제로 누르면 프레임이 빈 화면이 된다 | `click({force:true})` 가 요소 안정화 전 좌표를 눌러 빗나감 |
| "P08 링크·체크박스 결과가 실행마다 달라짐" (2A) | 항상 같은 결과다 | 같은 이유 (빗나간 클릭이 일부 실행에서만 맞음) |

**P08 불안정성 조사 결과:** 앱의 기능 문제가 아니라 **자동 검증 도구의 문제**였다.
요소의 실제 좌표를 `page.mouse.click` 으로 누르면 원본·재번들 모두 항상 같다. 도구는 이에 맞게 고쳤다
(`tools/verify_render.cjs`, `tools/probes/`).
추가로 헤드리스 Chromium 의 빈 화면 캡처와 글자 가장자리 렌더링 차이도 도구 쪽에서 처리했다
(`docs/EXTRACTION.md` 8절).

## E. STEP 2C 에서 새로 생긴 한계

- 신규 화면의 버튼·칩·중요도 선택기는 모두 정적이다 (선택해도 바뀌지 않음). 동작은 STEP 3.
- 화면의 가격(154,000원), 공연명 일부(〈별빛 아래〉, 〈Night Drive〉), 판정 결과는 가상 데이터다.
- 캐스팅 조건은 가상 뮤지컬 화면에서만 보여준다. 실제 캐스팅 데이터 구조는 확인하지 않았다.
- 보조 보드 6개를 추가해 보드가 16개가 됐고 푸터 번호는 기존 `n / 10` 체계에 `· A-2` 같은 꼬리표를 붙였다. 기존 번호 체계의 불일치(B-3)는 그대로다.
- 예외 보드(P11)는 폰 6개라 오른쪽 여백이 남는다 (구성 변경 없이 둠).

## F. STEP 3C 이후 상태 (연석 만들기 체험 폰)

동작하는 범위와 테스트는 `docs/STEP3C_PAIR.md` 를 보라. P12 보드 1번 폰만 체험할 수 있고, 2~4번 폰과 P13 보드는 정적이다.
옆자리 관객 화면(PairReceive), 수신 동의 등록(PairIntent), 여러 후보 동시 제안은 구현하지 않았다.

### STEP 4 에서 다룰 UX/UI 문제

1. 공용 상태 화면 문구가 일반 교환 기준이다. 연석 흐름에서도 그대로 보인다.
   - StatusSent 타임라인: '교환 신청 · 조건 등록 완료', '후보 발견 · 양방향 조건 확인 통과', '내 수락(동의) 완료'
   - ExCancelled: '교환 신청을 취소했어요'
   - 특히 '수락(동의)' 표현은 연석의 '제안 수신 동의'와 헷갈릴 수 있다.
2. 용어가 섞여 있다: '교환 의향 등록', '제안 수신 동의', '의향을 등록한 옆자리'가 PairSeat, PairDone, PairReceive, PairIntent에서 함께 쓰인다.
   - PairDone의 '의향을 등록한 다른 후보에게 보낸 제안은 닫혔어요'는 지금의 '한 번에 한 명에게 제안' 모델과 맞지 않는다.
3. 지킬 좌석과 내놓을 좌석이 좌석 방향 화면(PairSeat)의 라디오 설명에서 처음 나온다.
   - 교환 방식 화면에서는 어느 티켓을 내놓게 되는지 알 수 없다.
4. '후보 아님' 카드가 개인 정보 문제를 낳을 수 있다. 특정 좌석의 관객이 수신 동의를 하지 않았다는 사실이 드러난다. 완전히 숨기는 방안을 검토해야 한다.
5. 연석 후보 확인 화면의 밀도가 높다.
   - 7열 방향처럼 카드 2개가 모두 펼쳐지면 본문 높이에 여유가 거의 없다.
   - 보드에서는 0.58배로 축소돼 11px 글자를 읽기 어렵다.
   - 제안 보내기 전 확인 화면의 '내 좌석 (지금)' 칸은 3줄로 줄바꿈된다.
6. 거절 뒤 '다른 후보 확인하기'로 갔을 때 후보가 없으면 안내 문구만 있다. 반대 방향으로 가는 버튼을 바로 주지 않는다.
7. 데모 모드 패널(11열 5번 관객 상황 바꾸기, 상대방 수락·거절)이 휴대폰 화면 안에 있다. 점선 상자로 구분했지만 실제 UI로 오해할 수 있다.
8. P13 정적 보드의 보내기 버튼이 비활성으로 보인다. 확인 체크박스는 누를 수 있어 보이지만, 정적 화면이라 눌러도 버튼이 활성화되지 않는다.
9. 연석 흐름에는 단계 표시(예: 2/4)가 없다. 일반 교환과 진행 표시 방식이 다르다.
10. 새로고침하면 처음 상태로 돌아간다. 화면 전환을 스크린 리더에 알리는 안내(aria-live)가 없다.

| 10. aria-live | 해결. 화면 제목과 상태만 짧게 알린다. 새로고침 시 상태 유지는 여전히 없다 |

PairReceive·PairIntent 는 이제 P12 3번 폰에서 동작한다. P13 상태 보드의 같은 화면은 정적 장면이다.

### 남은 UX/UI 문제 (STEP 4B 이후)

1. 보드 위 휴대폰 화면이 0.58배로 축소돼 12px 글자도 실제로는 약 7px로 보인다. 평가자가 확대 없이 읽기 어렵다.
2. 시연 제어판의 위치가 보드마다 다르다 (P08 은 제목 오른쪽, P12 는 오른쪽 카드 아래). 일관된 자리와 시각 규칙이 필요하다.
3. 수신자 폰은 3번 위치에 있어 신청자 폰(1번)과 떨어져 있다. 두 사람의 상호작용을 한눈에 보기 어렵다.
4. 제안 검토 화면은 수락 뒤에도 '다른 좌석으로 옮기자는 교환 제안이에요' 제목이 그대로다. 상태별 제목이 필요하다.
5. 응답 기한, 신청 횟수 같은 가상 규칙은 문구로만 있다 (카운트다운 없음).
6. 여러 후보에게 동시에 제안하는 모델은 다루지 않는다 (한 번에 한 명).
7. 새로고침하면 체험 상태가 사라진다.
8. 실제 배치도 데이터 구조, 좌석별 교환 정책, 동행 좌석 분리 정책은 확인하지 않았다 (모두 시연 판정).

### 남은 UX/UI 문제 (STEP 4C 이후)

1. 보드 위 축소 화면 자체는 여전히 작다. 크게 보기를 눌러야 읽을 수 있다. 인쇄나 PDF 로 내보낼 때는 크게 보기를 쓸 수 없다.
2. 크게 보기 버튼(30px)이 보드 위에서는 약 30px 이지만, 노트북 화면에서 보드 전체가 축소되면 작게 보인다.
3. 진행 현황 화면은 세로 타임라인을, 다른 화면은 가로 단계 표시를 쓴다. 의도한 구분이지만 같은 흐름에 두 가지 표현이 있다.
4. 신청 현황(Waiting)은 원래 세로 진행 목록을 쓰므로 공용 단계 표시가 없다.
5. 표지(P01)의 폰은 크게 보기가 없다 (장식용).
6. 수신자 '제안 도착' 상태는 설정 화면의 알림 카드로만 보인다. 실제 앱의 푸시 알림·알림함은 다루지 않았다.
7. 체험 폰을 확대한 상태에서 보드의 시연 제어판은 배경 막 뒤에 가려진다. 결과 조작(최종 확인 등)을 하려면 확대를 닫아야 한다.
