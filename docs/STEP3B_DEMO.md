# STEP 3B: 일반 좌석·회차 교환 인터랙션 (체험 폰)

**어디서 체험하나:** P07 UI 좌석·회차 교환 보드의 **1번 폰**(예매 상세). 처음 화면은 기존과 같고, 캡션에
"이 폰은 직접 눌러 체험할 수 있어요 (데모)"를 붙였다. 다른 폰(2~6번)과 다른 보드는 기존 정적 시연 그대로다.

모든 티켓·조건·가격·판정은 **시연용 모의 데이터**다. 실제 예매처의 티켓을 바꾸거나 결제하지 않는다.
상대방의 수락·거절과 최종 확인 결과는 화면의 **'데모 모드 … 시뮬레이션'** 버튼으로 사용자가 직접 정한다.

## 1. 실제로 동작하는 인터랙션

| 화면 | 동작 |
|---|---|
| 예매 상세 | '좌석·회차 교환 신청' → 조건 등록 |
| 조건 등록 | 회차 칩(현재 회차 '좌석만 교환' 포함), 구역 칩('상관없음'은 단독), 회차·구역·열 중요도(필수/선호/무관, 같은 값을 다시 누르면 '선택 필요'), 열 범위 −/+ , 입력이 부족하면 안내 문구가 주황으로 바뀌고 '교환 신청 등록' 비활성 |
| 신청 현황 | 등록한 조건과 중요도 요약(조건 유지), '수정'→조건 등록, '알림 도착(프로토타입)'→ 후보 탐색, '교환 신청 취소' |
| 양방향 조건 확인 | 내 조건↔후보 티켓, 후보 조건↔내 티켓을 각각 계산해 표시. 충족/선호와 달라요(이유 설명)/불일치/비교 안 함/확인 필요, 미확인 정보 건수 |
| 교환 전후 비교 | 공연명·날짜·회차·구역·열·좌석·캐스팅·권종·가격·정책 확인을 모의 데이터에서만 표시(없으면 '확인 필요'). 동의 체크 전에는 '교환 제안 보내기' 비활성 |
| 진행 현황(상대방 검토) | 데모: 상대방 수락 / 상대방 거절, '제안 취소하기' |
| 상대방 수락 | "아직 교환이 완료된 것은 아니에요", 데모: 최종 확인 시작, '교환 취소하기(최종 확인 전)' |
| 최종 확인 중 | 데모: 최종 확인 성공 / 실패 (이 단계에서는 취소 불가) |
| 교환 완료 | 받은 티켓·이전 티켓·예매번호를 선택한 후보 데이터로 표시. '예매 내역으로' → 처음 상태 |
| 예외 5종 | 필수 불일치(조건 수정 / 내 쪽 필수만 선호로 바꾸기, 상대 필수일 때는 비활성), 후보 없음(조건 수정 / 신청 취소), 상대방 거절(다른 후보 찾기 / 신청 취소), 신청 취소(다시 신청 / 예매 상세로), 최종 확인 실패(내 티켓 확인 / 다시 신청) |
| 공통 | 헤더 뒤로(진행 중에는 머무름), Esc = 처음 상태, 화면 전환 후 포커스 유지, 다른 화면에 다녀와도 입력 유지 |

## 3. 상태 관리 구조

```
P07 페이지 로직 (DCLogic)
  state = { stacks: 폰별 화면 기록, demo: 엔진 상태 }
  onclick (폰 틀) ─ 체험 폰이고 data-act 가 있으면 → DEMO.reduce(state, action) → {state, nav}
                  └ 아니면 기존 STEP 3A 링크 전환
  renderVals → demo = DEMO.views(state) → 1번 폰의 각 컴포넌트에 demo="{{demo}}" 로 전달
컴포넌트 (MatchCheck 등): demo 가 있으면 그 데이터를, 없으면 DEFAULT_VIEW(같은 엔진으로 계산한 기본 장면)를 그림
```

- 엔진 상태: `cond`(회차·구역·열·캐스팅과 각 중요도), `step`, `candId`, `consent`, `declined`(거절한 후보)
- 단계(step): edit → searching(교환 신청) → found(후보 발견) / mismatch / none → proposed(제안 전송·상대방 검토)
  → accepted(상대방 수락) → final(최종 확인 중) → done / failed, 그리고 declined / cancelled
- 버튼은 템플릿에 `data-act` 속성만 있고, 동작은 엔진 한 곳에서 정한다. 같은 컴포넌트가 다른 폰·보드에서는 아무 동작도 하지 않는다.

## 4. 매칭 규칙과 예외 처리

- **양방향 계산:** A의 조건을 B의 티켓에, B의 조건을 A의 티켓에 각각 적용한다.
- **조건 판정:** 충족 / 필수 불일치(제외) / 선호 불일치(후보 유지 + 차이 설명) / 무관(비교 안 함) / 정보 없음(확인 필요).
- **결과:**
  - 양쪽 필수 모두 충족 → **후보 발견**(선호 차이가 적은 순서). 매칭 완료가 아니다.
  - 선택한 회차에 티켓은 있지만 어느 한쪽 필수가 불일치 → **필수 조건 불일치**(가장 가까운 후보와 이유)
  - 선택한 회차에 티켓 없음 → **후보 없음**
  - 필수 조건의 정보가 없으면 후보로 확정하지 않는다.
- **입력 검증:** 회차 1개 이상, 구역 선택(또는 상관없음), 중요도 미선택 없음. 미선택을 '무관'으로 처리하지 않는다.
- **완료 조건:** 동의 체크 → 제안 전송 → 상대방 수락 → 최종 확인 성공 순서를 모두 거쳐야 '교환 완료'를 보여준다.
- **모의 데이터 (후보 4장):**

  | 후보 | 티켓 | 소유자 조건 | 정보 없음 |
  |---|---|---|---|
  | C1 | 12.21 14:00 · R석 A구역 5열 8번 | 회차 12.20 18:00 필수, A구역 선호 | 가격, 정책 |
  | C2 | 12.20 18:00 · R석 A구역 6열 3번 | 회차 12.20 18:00 필수, B구역 필수, 1~10열 선호 | - |
  | C3 | 12.19 19:30 · R석 B구역 9열 4번 | 회차 12.20 14:00 필수 | - |
  | C4 | 12.21 14:00 · R석 C구역 2열 7번 | 회차 12.20 18:00 필수, C구역 필수 | - |

## 7. 아직 정적이거나 구현하지 않은 것

- 캐스팅: 엔진은 캐스팅 조건(정보 없으면 확인 필요)을 지원하지만 체험 공연이 콘서트라 입력란은 '이 공연은 해당 없음'. 캐스팅이 있는 가상 뮤지컬 화면(P09 조건 설정)은 정적이다.
- 후보는 한 명만 보여준다 (여러 후보 중 선택 없음). 응답 기한 카운트다운은 정적 문구.
- 정적 보드: P09·P10·P11·P13·P15 등 보조 보드의 화면, P07 보드 2~6번 폰, 연석 만들기(P12·P13) 흐름, 표지.
- 교환 자격 확인 3상태(P09)·티켓 상태 변경 예외(P11)는 체험 흐름에 연결하지 않았다.
- '모바일 티켓 보기', '공연장 안내', '예매 취소' 등 정보성 버튼은 동작 없음.
- 새로고침하면 처음 상태(저장하지 않음). 화면 전환 시 스크린 리더 안내(aria-live) 없음.
