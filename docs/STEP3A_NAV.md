# STEP 3A: 기존 화면 전환 정상화

## 1. 링크 오류의 실제 원인 (확인됨)

`tools/probes/probe_link_cause.cjs` 로 **원본 HTML** 에서 측정했다.

| 확인 항목 | 결과 |
|---|---|
| 링크 href | `Request.dc.html` 등 **상대 경로** (P07 보드 5종: Request, Main, Waiting, Match, Done) |
| 페이지 프레임 문서 주소 | `blob:null/<uuid>` (로더가 페이지마다 blob 문서를 만들어 iframe 에 넣음) |
| baseURI / `<base>` 태그 | baseURI = 같은 blob 주소, `<base>` 없음 |
| 상대 경로 해석 | `new URL('Request.dc.html', document.baseURI)` → **"Invalid URL" 오류**. blob URL 은 상대 경로의 기준이 될 수 없다. `a.href` 도 해석되지 않은 원문을 돌려준다 |
| iframe 보안 속성 | `sandbox`, `allow` 없음. origin 은 `null` |
| 이동 대상 | 상위 프레임이 아니라 **그 페이지 iframe 자신**이 `about:blank#blocked` 로 이동 (Chromium 이 해석 실패한 이동을 막는 방식) |
| 같은 문서 안 이동 | `#해시` 링크는 정상 (문서 유지) |
| 런타임(support.js) | 클릭 처리·`preventDefault`·화면 전환 코드가 **없음**. 링크 정리 함수(`pt`)는 드래프트 모드에서만 쓰여 번들에서는 동작하지 않음. `dc-import` 는 이름을 템플릿 해석 때 한 번 읽고 고정 |

결론: 원래 디자인 도구에서 "옆 파일(다른 화면)로 이동"하던 링크가, 단일 HTML 번들의 blob 문서 안에서는
해석할 기준 주소가 없어 브라우저가 이동을 차단한 것이다. 설령 해석되더라도 `Request.dc.html` 이라는 파일은 번들 안에 없다.

## 3. 화면 간 이동 구조

- 각 폰 화면 틀(기존 `scale` div)에 `data-nav-host`, `onclick`, `onkeydown`, `tabIndex="-1"` 을 붙였다.
- 그 보드에 실제로 있는 화면을 모두 미리 그려 두고(`<form data-nav-screen>` 로 감쌈) `display` 로만 바꾼다.
  - `form` 으로 감싼 이유: 같은 화면이 여러 폰에 있으면 라디오 `name` 이 문서 전체에서 한 그룹이 되어 기본 선택이 풀렸다. form 단위로 그룹이 분리된다.
  - 기존 `<button>` 은 type 이 없어 제출 버튼이므로 `onsubmit` 에서 제출을 막는다.
- 링크 클릭은 자식 컴포넌트에서 폰 틀로 버블링되고, 다음 규칙으로 처리한다.

| 상황 | 동작 |
|---|---|
| `X.dc.html` 이고 X 가 이 보드에 있음 | 같은 자리에서 X 로 전환 (기록에 추가) |
| X 가 이 보드에 없음 | 기본 이동만 막고 **현재 화면 유지** |
| `aria-label="뒤로"` + 이전 기록 있음 | 이전 화면으로 |
| `aria-label="뒤로"` + 이전 기록 없음 | 링크가 가리키는 화면으로 (보드에 있을 때) |
| Esc (폰 안에 포커스) | 그 폰의 처음 화면으로 |
| 화면이 바뀜 | 누른 링크가 숨겨지므로 포커스를 폰 틀로 옮김 (키보드 위치 유지) |

- 폰마다 기록이 따로이며, 한 폰의 이동은 다른 폰에 영향을 주지 않는다.

## 5. 여전히 이동할 수 없는 화면 (현재 화면 유지)

| 보드 | 링크 | 목적지 | 이유 |
|---|---|---|---|
| P01 표지 | 조건 등록의 뒤로·교환 신청 등록, 교환 제안의 뒤로·거절·교환 수락 | Main, Waiting, Done | 표지 보드에 없는 화면 |
| P10 처리 상태 | 교환 완료의 예매 내역으로 | Main | 이 보드에 없는 화면 |
| P12 연석 | 교환 신청의 뒤로, 연석 완료의 예매 내역으로 | Main | 연석 보드에 없는 화면 (일반 교환 보드에 있음) |

보드는 서로 다른 문서(iframe)라 보드 사이 이동은 하지 않았다. STEP 2C 신규 화면 18개에는 링크가 없고 버튼은 여전히 정적이다.

**목적지가 불명확하거나 2C 원칙과 어긋나는 링크** (바꾸지 않고 기록만 함):

| 링크 | 현재 목적지 | 문제 |
|---|---|---|
| 교환 제안 → 교환 수락 | 교환 완료(Done) | STEP 2C 원칙(수락 ≠ 완료)에 따르면 '상대방 수락/최종 확인 중'이 맞지만, 그 화면은 P10 보드에 있음 |
| 옆자리 관객 화면 → 수락하기 | 연석 완료(PairDone) | 같은 문제 (PairAccepted 는 P13 보드에 있음) |
| 교환 제안 → 거절 | 신청 현황(Waiting) | 받는 쪽의 거절 후 화면인지, 거절 상태 화면(ExDeclined, P11)이 맞는지 불명확 |
| 신청 현황 → 알림 도착 | 교환 제안(Match) | STEP 2C 에서 Match 를 받는 쪽 시점으로 정리해, 신청자의 다음 화면으로는 시점이 바뀜 |
| 표지·연석의 '예매 내역으로' | Main | 다른 보드의 화면 |

## 6. 입력 상태 보존

- 화면을 지우지 않고 숨기기만 하므로 **다른 화면에 다녀와도 입력 상태가 유지**된다 (교환 방식 라디오를 바꾸고 → 다음 → 뒤로 → 선택 유지, 테스트로 확인).
- 전환 이후에도 라디오·체크박스가 정상 동작한다.
- 새로고침하면 처음 화면과 기본 선택으로 돌아간다 (저장하지 않음).

## 8. 시각적 회귀 (`verify/results-3a/regression-vs-2c.txt`)

STEP 2C 커밋 빌드와 비교했다.
- 데스크톱 1920×1080 보드 16장: **15장 픽셀 동일**, 다른 1장은 의도한 P11 정렬 변경
- 모바일 390px 뷰포트 16장: 15장 동일, 다른 1장은 P11
- 보드 제목·크기·모바일 가로 스크롤 폭·콘솔 로그: 동일
- 보이는 링크·입력 요소, 라디오·체크박스 클릭 결과, Tab 순서: 동일 (P12 라디오 결과의 '클릭한 요소 순번'만 숨겨진 복제 화면 때문에 4·5 → 10·11 로 달라짐, 상태 값은 6단계 모두 같음)
- 첫 링크 클릭: 이전 `about:blank#blocked`(본문 0자) → 이후 blob 문서 유지(본문 정상) — 이번 수정의 목적

초안에서 발견해 고친 회귀: 같은 화면을 여러 폰에 그리자 라디오 기본 선택이 풀려 P12 에 121px 차이가 났다 → form 으로 그룹 분리 후 0.
