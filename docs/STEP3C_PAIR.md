# STEP 3C: 연석 만들기 인터랙션 (체험 폰 · 실험 기능 · 수요 미검증)

P12 보드(**P08 UI 연석 만들기**)의 **1번 폰**을 직접 눌러 볼 수 있는 연석 만들기 프로토타입으로 바꿨다.
STEP 3B의 매칭 엔진, 상태 관리, 화면 전환 구조를 그대로 다시 쓴다. 다른 폰(2~4번)과 P13 상태 보드는 같은 엔진으로 계산한 정적 장면을 보여준다.

- 모든 좌석·배치도·수신 동의·정책 판정은 **시연용 모의 데이터**다. 실제 예매처, 결제, 티켓 변경과는 연결되지 않는다.
- 옆자리 관객의 수신 동의 상태와 수락·거절, 최종 확인 결과는 **데모 모드 버튼으로만 일어나는 시뮬레이션**이다.
- 연석 수요는 검증하지 않았다. 화면의 '실험 기능 · 수요 미검증' 표시는 그대로 둔다.
- 최종 확인에 실패해도 원래 티켓이 유지된다는 내용은 **목표 UX·시스템 요구사항**으로만 표기한다. NOL이 보장하는 기능으로 쓰지 않는다.

## 1. 시나리오와 모의 데이터

A(나)는 같은 회차(12.20 (일) 18:00 · 3회차)의 떨어진 R석 2장을 갖고 있다. **7열 12번**과 **11열 4번**이다.
A는 한 장을 지키고(지킬 좌석) 다른 한 장을 옆자리 관객 B에게 내놓는다(내놓을 좌석).
요청 예시의 F6/F4는 기존 화면의 좌석 데이터(7열·11열)에 맞춰 바꿨다.

| 지킬 좌석 → 내놓을 좌석 | 옆자리 | 수신 동의 | 배치도 판정 | 결과 |
|---|---|---|---|---|
| 11열 4번 → 7열 12번 (기본) | 11열 3번 | 없음 | — | 후보 아님 (제안하지 않음) |
| | 11열 5번 | 데모에서 바꿈 | 같은 블록 · 통로 없음 | 상황에 따라 다름 (아래) |
| 7열 12번 → 11열 4번 | 7열 11번 | 있음 | 배치도 데이터 없음 | **인접 여부 확인 필요** → 제안 보류 |
| | 7열 13번 | 있음 | 번호는 이어지지만 12·13번 사이 통로 | **인접 아님** → 제안 불가 |

11열 5번 관객의 상황(데모 모드 칩): 기본 / 동행 좌석 있음 / 조건 불일치 / 자격 미확인 / 동의 없음.

| 상황 | 판정 | 제안 |
|---|---|---|

## 2. 실제로 동작하는 인터랙션 (P12 보드 1번 폰)

| 화면 | 동작 |
|---|---|
| 교환 방식 선택 (PairMode) | 티켓 2장 체크(1장만 고르면 진행 불가 안내), 티켓별 '교환 가능 (시연 판정)' 표시, 교환 방식 라디오(좌석·회차 교환을 고르면 07 일반 교환 보드 안내 후 머무름), 다음 |
| 좌석 방향 (PairSeat) | '11열로 모으기 / 7열로 모으기' 라디오 = 지킬 좌석 선택. 배치도에 지킬 좌석·내놓을 좌석·옆자리·통로가 바로 반영됨 |
| 연석 후보 확인 (PairAdjacency, 데이터 템플릿으로 재작성) | 지킬 좌석의 왼쪽·오른쪽 옆자리 판정 카드(수신 동의, 인접 여부, 교환 자격, 상대 조건 ↔ 내가 줄 좌석, 동행 좌석), 제안 가능한 후보만 선택, 데모 모드에서 11열 5번 관객 상황 바꾸기 |
| 제안 보내기 전 확인 (PairWarn, 재작성) | 지금/완료 시 좌석, 상대의 좌석 변화, **양방향 확인**(① 내 조건: 지킬 좌석 바로 옆 ② 상대 조건 ↔ 내가 줄 좌석), "아직 '매칭 완료'가 아니에요", 동행 분리 경고, 확인 체크 후에만 보내기 |
| 상대방 검토 (StatusSent, 3B 화면 재사용) | 데모 모드: 상대방 수락 / 상대방 거절, 제안 취소 |
| 상대방 수락 (PairAccepted) | 완료 아님 안내, 지금/통과 시 좌석, 데모 모드: 최종 확인 시작, 교환 취소 |
| 최종 확인 중 (StatusFinal, 재사용) | 데모 모드: 최종 확인 성공 / 실패 |
| 연석 완료 (PairDone) | 바뀐 좌석·내놓은 좌석, 예매 내역으로(처음 상태) |
| 거절 (PairDeclined) | 내 좌석 변경 없음, 거절한 후보, 다른 후보 확인하기(거절한 후보는 '거절됨'으로 선택 불가) / 반대 방향으로 모으기 보기 |
| 취소 (ExCancelled, 재사용) · 최종 확인 실패 (ExFinalFailed, 재사용) | 2장 모두 유지(목표), 다시 신청(고른 방향 유지), 처음으로 |

- 화면 위쪽 '뒤로': 선택을 유지한 채 이전 화면. 제안을 보낸 뒤(검토·수락·최종 확인 중)에는 머무르고 '취소'로만 나간다.
- Esc: 체험 폰을 처음 상태로 되돌린다 (입력 요소 포함).
- 모든 버튼과 입력은 키보드(Tab·Enter·Space)로 조작된다. 화면이 바뀌면 포커스를 폰 틀로 옮긴다 (STEP 3A와 같다).

## 3. 판정 규칙 (`tools/authoring/demo3c_pair.js`)

**실제 인접 여부** `adjacency(지킬 좌석, 옆자리)`: 다음 순서로 확인한다. 좌석 번호가 이어지는 것만으로는 인접으로 판단하지 않는다.
1. 같은 회차
2. 같은 구역·열
3. 번호 연속
4. 배치도 확인 범위: 범위 밖이면 `unknown`, 화면에는 '인접 여부 확인 필요'
5. 같은 블록: 블록이 다르면 통로로 분리된 것으로 보고 `no`

**후보 판정** `judgeCandidate`:
- 수신 동의가 없으면 `hidden`: 후보로 보여주지 않고 제안도 보내지 않는다.
- 동의가 있으면 아래 우선순위로 판정한다.
  1. 이미 거절된 후보
  2. 인접 아님
  3. 상대 필수 조건 불일치
  4. 인접 확인 필요
  5. 교환 자격 확인 필요
  6. 동행 좌석의 좌석별 교환 정책 확인 필요
  7. 위에 해당하지 않으면 제안 가능
- 동행 좌석은 예매 1건에 좌석이 여럿이라는 이유만으로 막지 않는다. 경고를 보여주고 상대가 거절할 수 있게 한다. 좌석별 교환 정책을 모르면 '확인 필요'로 보류한다.
- 확인되지 않은 항목이 하나라도 있으면 '제안 가능'으로 표시하지 않고, 선택 버튼도 비활성으로 둔다.

**양방향 확인**:
- 내 쪽: 지킬 좌석 바로 옆인지 (배치도 기준)
- 상대 쪽: 상대가 등록한 조건을 내가 내놓을 좌석에 적용한다. STEP 3B의 `DEMO.evaluate`를 그대로 쓴다.
- 양쪽이 모두 맞아도 상대 수락과 최종 확인 전에는 '매칭 완료'로 표시하지 않는다.

## 4. STEP 3B에서 다시 쓴 것과 새로 만든 것

- 테스트: `test_demo_flows.cjs`의 클릭 도우미, 잘림 기록, 스크린샷 방식

**새로 만든 것**
- 연석 판정: 배치도 인접, 수신 동의, 동행 좌석
- 연석 상태와 행동:
  - 선택: pick, mode, next, dir, toCandidates, profile, choose, toWarn
  - 제안: ack, send
  - 거절 이후: otherCandidate, otherDir
  - 다시 시작: restart, home
  - 이동: back
- 화면 데이터: views, defaultViews

**페이지 로직의 차이**: STEP 3B 로직의 다음 다섯 곳만 바꿨다.
- 엔진 이름: `ENGINE = PAIR`
- 입력 요소 처리: 기본 동작을 막지 않는다.
- Esc 처리: `ENGINE.reset`을 부른다.

## 7. 회귀와 의도한 변경

STEP 3B 커밋 빌드와 비교한 결과(`regression-vs-3b.txt`):
- 데스크톱 16장 중 14장, 모바일 16장 중 15장이 픽셀 단위로 같다.
- 보드 제목과 크기, 모바일 가로 스크롤 폭이 같고, 콘솔 로그는 0건이다.

의도한 차이는 다음과 같다.

**P12 (2~4번 폰, 정적)**
- 배치도에 '내놓을 좌석'(테두리)과 12·13번 사이 통로(점선)를 표시했다.
- 옆자리 강조는 지킬 좌석의 이웃(11열 3·5번)만 한다. 범례는 '지킬 좌석 / 내놓을 좌석 / 옆자리 / 통로'로 바꿨다.
- 티켓마다 '교환 가능 (시연 판정)'을 표시했다.
- 1번 폰 캡션에 '직접 눌러 체험할 수 있어요 (데모)'를 붙였다.

**P13 (정적)**
- 후보 확인 화면은 '지킬 11열 4번' 방향의 옆자리 2곳만 보여준다.
  - 이전 화면은 두 방향의 후보 3개를 섞어 보여줬고, 7열 13번을 '확인 필요'로 표시했다.
  - 바뀐 배치도 모의 데이터에서 7열 13번은 '통로로 분리'로 판정되며, 7열 방향을 고르면 1번 폰에서 볼 수 있다.
- 보내기 전 확인 화면에 양방향 확인과 '아직 매칭 완료 아님' 문구를 넣었다.
- 확인 체크 전에는 보내기 버튼을 비활성으로 표시한다.
- 수락 화면에 '교환 취소하기 (최종 확인 전)' 버튼을 넣어 일반 교환의 수락 화면과 맞췄다.
- 타임라인 문구 '내 수락(동의) 완료'를 '내가 제안을 보냈어요 (내 수락)'으로 바꿨다. 수신 동의와 수락이 헷갈리지 않게 하기 위해서다.

**nav 테스트 61→59건**: P12 1번 폰의 교환 방식 화면에 있던 '뒤로 → Main' 링크가 체험 폰에서는 상태 기반 뒤로 버튼으로 바뀌었다. 이 링크를 검사하던 2건(링크 + Esc)이 빠졌다.
- 뒤로 버튼은 연석 여정 9가 검사한다.
- 입력 유지 검사(4번)는 STEP 3A 링크 전환만 쓰는 2번 폰으로 옮겼다. 1번 폰에서 '좌석·회차 교환'을 고르면 다음 화면으로 가지 않는 것이 의도된 동작이기 때문이다.

## 8. 아직 구현하지 않은 것

- 옆자리 관객(B)의 화면(PairReceive)은 정적이다. B의 수락·거절은 상태 화면의 데모 버튼으로만 시뮬레이션한다.
- 제안 수신 동의를 등록하는 화면(PairIntent, P13)은 정적이다. 동의 상태는 데모 칩으로만 바꾼다.
- 한 번에 한 명에게만 제안한다. 여러 후보에게 동시에 보내는 동작과 '다른 제안 자동 닫힘'은 문구로만 있다.
- 배치도는 모의 데이터다 (12·13번 사이 통로 하나, 7열 1~11번은 데이터 없음). 실제 공연장 배치 데이터는 확인하지 않았다.
- 응답 기한, 신청 횟수 같은 가상 규칙은 정적 문구다.
- '모바일 티켓 보기' 같은 정보성 버튼은 동작이 없다.
- 새로고침하면 처음 상태로 돌아간다. 화면 전환 시 스크린 리더 안내(aria-live)는 없다. 다만 진행 불가 안내에는 `role="status"`를 붙였다.
